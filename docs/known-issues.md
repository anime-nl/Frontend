# Known issues

Bugs and gaps that were found while working on something else. Fix them in their own change, with a test, and move the entry to "Fixed" (or delete it).

Format: **title** (where): what is wrong. Mark anything not yet reproduced as _unverified_.

## Open

- **`typescript` cannot be bumped past 7.0.2 yet** (`package.json`): Dependabot's PR #2 bumps `typescript` from 5.9.3 to 7.0.2, but `bun run typecheck` then fails with `Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './lib/tsc' is not defined by "exports"`. TypeScript 7 does not yet expose the stable programmatic API that `vue-tsc`/Vue's language tooling needs; confirmed as a known, currently unfixable limitation in [vuejs/language-tools#6124](https://github.com/vuejs/language-tools/issues/6124) and [#6156](https://github.com/vuejs/language-tools/issues/6156) (both closed `not_planned`), and by [Microsoft's own TypeScript 7 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#typescript-and-embedded-languages), which says Vue projects "will need to continue using TypeScript 6.0 for now". There is no newer `vue-tsc` release to bump to (3.3.11, already installed, is latest and still fails). Revisit once `vue-language-tools` ships v4 with real TS 7 support (tracked in their alpha PR [#6170](https://github.com/vuejs/language-tools/pull/6170)); until then, leave PR #2 open or add an `ignore` rule for `typescript` major versions in `.github/dependabot.yml`.

- **Trustpilot score is hardcoded** (`app/utils/navigation.ts`, `badge: '4.0'`): it will go out of date. Tried replacing it with a live TrustBox widget, but it was reverted at the shop owner's request: the chosen template did not show the numeric score, it broke the navbar's centering, and Trustpilot's widget styling does not fit the site's theme (only height/width/theme/locale are customizable). A live score would need either a different, better-fitting TrustBox template plus a navbar layout that isolates it from the centered nav, or fetching the score server-side through the Trustpilot API (needs API credentials, which are not available in this repo).

- **`@variablevic/mollie-payments-medusa` cannot report a payment as "still processing", only success or a hard failure** (`server/api/checkout/complete.post.ts`, `app/pages/checkout/return.vue`): the plugin's `authorizePayment` throws a plain `INVALID_DATA` MedusaError ("Payment is not authorized: current status is <status>") for any Mollie status other than `captured`/`authorized`/`paid`, and Medusa re-throws it from `carts/{id}/complete` instead of answering with its graceful `PAYMENT_REQUIRES_MORE_ERROR` shape. Mitigated, not fixed: the complete route now reads the Mollie status out of that error message (`open`/`pending` stay pending, `failed`/`canceled`/`expired` become failed, anything it cannot parse stays pending), and the return page asks again every 3 seconds for about a minute. This depends on the plugin's exact error wording, so re-check `mollieStatusFromError` after a plugin upgrade; a real fix would fork the plugin or give the Nuxt server a Mollie API key to read the payment status directly.

- **`@variablevic/mollie-payments-medusa`'s peer deps are pinned to Medusa 2.5.1** (`medusa/package.json`): well behind the `2.21.1` this repo runs. There is an [open upstream issue](https://github.com/variablevic/mollie-payments-medusa/issues/7) reporting `"Unable to retrieve the payment provider with id: pp_mollie"` on 2.7.0 because of it. Verified during Phase 4 (Mollie payments) against a throwaway Medusa 2.21.1 instance, on a scratch Postgres database created and dropped for the check (never touching the shared dev database or the live `medusa` container): the plugin registers cleanly (`GET /store/payment-providers?region_id=<id>` lists `pp_mollie-hosted-checkout_mollie`) and a payment-session request reaches Mollie's real API (clean auth rejection with a dummy key, not a crash). So the pin did not reproduce here — no fork-and-fix was needed — but re-verify with the same check after any future Medusa or plugin version bump, since the issue is real and version-dependent.

- **No Mollie payment can be created in the dev container at all — `MEDUSA_URL` is unreachable from Mollie's side** (`.devcontainer/docker-compose.yml`, the `medusa` service's `MEDUSA_URL: http://localhost:9000`): `@variablevic/mollie-payments-medusa` unconditionally builds a webhook URL as `medusaUrl + '/hooks/payment/...'` (`mollie-provider.js`, no config option to disable it) and passes it to Mollie's `payments.create`. Verified with a real Mollie test API key against a throwaway scratch Medusa instance: cart creation, the payment-collection, and the request itself (billing address, amount, currency) all passed Mollie's validation, but creation itself failed with `{"type":"invalid_data","message":"The webhook URL is invalid because it is unreachable from Mollie's point of view."}` — Mollie actively checks reachability, not just the hostname string. `localhost` can never satisfy that from inside the dev container, so this blocks the plan's own manual-verification step ("pay for a test order in Mollie's sandbox mode") until `MEDUSA_URL` points at a publicly reachable tunnel (e.g. `ngrok http 9000` or `cloudflared tunnel --url http://localhost:9000`, run on the host — the container's port 9000 is already mapped to the host's) pointed back at the dev container while testing. _To do: the user will run this manually later._

- **Medusa product catalog content is not translated** (`app/pages/product/[id]/index.vue`, `app/components/{categoryPage,productCard}.vue`): product titles, descriptions, option/variant names, category names, collection names and tags all come from Medusa, which has no per-locale content layer in this backend's current schema. The i18n rollout (nl/en/de) only translates storefront UI chrome — nav, buttons, forms, support/checkout copy, validation messages and emails — never this catalog content, so an English or German visitor still sees Dutch (or whatever language the catalog was entered in) product data. Fixing this needs a Medusa-side schema change (a translations table, or one product record per locale) that is out of this project's scope.

- **The Mollie payment-return flow always lands the customer on the unprefixed (Dutch) page, regardless of their chosen locale** (`server/api/checkout/payment-session.post.ts`, `medusa/medusa-config.ts`): the redirect URL Mollie sends the customer back to is `this.options_.redirectUrl` inside `@variablevic/mollie-payments-medusa`'s `initiatePayment` (`mollie-base.js:109`) — a single static value, read from the plugin's own config options (`redirectUrl: process.env.MOLLIE_REDIRECT_URL` in `medusa-config.ts`), never from any per-request `context`/`data` our `payment-session.post.ts` could pass when creating the session. The plugin does read a per-request `redirectUrl` from `input.data` (`mollie-base.js:355`), but only inside `updatePayment`, a different code path Medusa's standard checkout flow never calls. Unlike the OAuth callback fix above, there is no cookie-based workaround possible here: the return page is server-rendered fresh, so by the time it loads there is no client-side "locale from before" to read back from — only whatever the URL itself encodes. Fixing this for real needs forking the plugin so `initiatePayment` accepts a per-session `redirectUrl` override (the same "Step B scope" already deferred for the plugin's pending-vs-failed status issue above), or confirming Mollie's own API allows updating `redirectUrl` on an already-created, not-yet-paid payment (unverified — no live Mollie/Medusa backend available in this environment to test either approach).

## Fixed

- **Navbar links to pages that do not exist** (`app/components/navbar.vue`): only `/products`, `/products/tcg`, `/search`, `/product/[id]` and `/support` existed; the TCG/Figures/Plush/Keychains sub-links gave a 404. Added the missing parent and sub-category pages (`app/pages/products/**`), all built on a shared `CategoryPage` component and `useCategoryProducts` composable that resolve a Medusa category by handle. Since Medusa had no subcategories for Singles/Packs/Boosters, Prize/Scale/Noodle Figures or Acrylic/Metal keychains, `medusa/src/scripts/seed.ts` now creates them (as children of the existing top-level categories) and assigns the matching seed products to them. _The seed change is verified against Medusa's `CreateProductCategoryDTO` types but not run end-to-end (no local Postgres/Medusa in this environment) — reseed the dev database to pick it up._
- **Most icons loaded from the Iconify API at runtime** (`app/components/navbar.vue`): only `lucide` and `flat-color-icons` were installed locally. Installed the `@iconify-json/*` packages for `mdi`, `game-icons`, `material-symbols`, `material-symbols-light`, `simple-icons`, `pinhead` and `at-icons`. `pinhead` and `at-icons` are not in Nuxt Icon's built-in list of recognized collection names, so its `local` auto-discovery silently skipped them; `nuxt.config.ts` now lists every collection explicitly in `icon.serverBundle.collections` so all nine are actually bundled server-side. Fixing this also surfaced two icon names that do not exist in `mdi` (`search`, `prize`); replaced with `magnify` and `trophy`. The navbar's icon list moved to `app/utils/navigation.ts`, with a test that checks every icon against its installed collection.
- **Medusa module debug logging was always on** (`nuxt.config.ts`, `medusa.debug: true`): now `!isProductionEnv(process.env.NODE_ENV)` (`shared/utils/env.ts`).
- **Secrets are baked into the build** (`nuxt.config.ts`): `runtimeConfig` reads `process.env` at build time, so changing `SMTP_PASS` or `MEDUSA_PUBLISHABLE_KEY` needs a rebuild. This is inherent to reading them via `process.env` in `nuxt.config.ts`; Nuxt already supports overriding any `runtimeConfig` key at runtime (no rebuild) via a `NUXT_`-prefixed environment variable, so no code change was needed. Documented in the README's new "Rotating a secret without a rebuild" section.
- **No rate limit on `POST /api/support`** (`server/api/support.post.ts`): added a per-IP in-memory rate limiter (`server/utils/rateLimit.ts`, 5 requests per 10 minutes, keyed by `x-forwarded-for`).
- **Support page copy needed a check by the shop owner**: confirmed with the shop owner and updated `shared/utils/support.ts` and `app/pages/support/index.vue` — shipping is 2 to 3 business days from when the order is placed; returns require the item to be unused and in its original packaging, and the customer pays for return shipping. Also updated in `AGENTS.md`.
- **Product cards never showed a price** (`app/components/productCarousel.vue`, `app/pages/products/tcg/index.vue`, `app/pages/search/index.vue`): these requested `variants.prices.*` (or nothing) without a `region_id`, but `productCard` reads `variants[0].calculated_price`. Now requesting `*variants.calculated_price` with a `region_id` resolved via the new `useDefaultRegionId` composable (search page already had a region id, just the wrong field).
- **Backorderable items in stock were capped at the stock quantity** (`app/pages/product/[id]/index.vue`, the `stock` computed): a backorderable variant now has no maximum quantity even while stock remains, matching a fully out-of-stock backorderable variant.
- **Test debt**: added tests for `server/api/{categories,collections,products,regions}.ts`, `app/pages/{index,products}` (`search` already had tests), and the components `productCard`, `productPageHeader` and `showcaseCarousel`.
- **Product page images were not centered vertically and/or zoomed correctly** (`app/pages/product/[id]/index.vue`): the `<img>` only had a `max-height`, so `object-contain` had no fixed box to center or scale within. Switched to a fixed `h-160 w-full object-contain object-center`.

- **The Google OAuth callback page always rendered/redirected in Dutch regardless of the customer's chosen locale** (`app/pages/account/callback/[provider].vue`): Google always redirects back to this page's fixed, unprefixed callback URL, so the route itself carries no locale and `useLocalePath()` alone couldn't help. Now reads the `i18n_redirected` cookie @nuxtjs/i18n already maintains (via `useCookieLocale()`) and passes it explicitly to `localePath()` for the final redirect to `/account`, landing the customer back in the locale they were browsing in before they left for sign-in.
- **`splitStreetAndHouseNumber` misfired on a street name that itself ends in a number** (`shared/utils/checkout.ts`): a real Dutch street like "Plein 1944" (Nijmegen) was split into street "Plein" and house number "1944" on blur, same as a genuine combined "Street 12"-style autofill value. Now treats a bare 4+ digit number with no letter/word addition (e.g. "1944", but not "1944A" or "1944 bis") as part of the street name instead of a house number, since a real Dutch house number is virtually never four digits. Does not fully solve the ambiguity (a street name ending in a smaller bare number, or a genuine 4-digit house number, can still misfire either way) but fixes the specific case found.
- **`productCard.vue` formatted price as a raw number + currency code, not through `formatCurrency`** (`app/components/productCard.vue`): showed e.g. "10.90 EUR" instead of "€ 10,90" / "10,90 €", and never changed with locale, unlike every other price display. Now uses `shared/utils/currency.ts`'s locale-aware `formatCurrency`.
- **"By series" links in the navbar did not work** (`app/components/navbar.vue`, `app/pages/search/index.vue`): the links passed a category _handle_ (`?category=tcg`) but the search page used it as a category _id_, so nothing was selected. The search page now accepts an id or a handle, and the links (`bySeriesLink`) also focus the Collection dropdown so the visitor picks the series. The Plush link used the handle `plushies`, which does not exist in the seed data; it is now `plush`. Handles in production must match `tcg`, `figures`, `plush` and `keychains`.
- **`bun run typecheck` failed with circular type errors** in `server/utils/medusa.ts` and every API route that uses it. Fixed by typing `medusaFetch` and the routes with `@medusajs/types`.
- **Support form let line breaks through into the email body** (`normalizeSupportRequest`). Fixed by collapsing line breaks in every field except the message.
- **`resolveShippingProfileId` treated an empty cart as all-Brievenbus** (`server/api/checkout/shipping-options.get.ts`): `itemProfileIds.every(...)` on an empty array is vacuously `true` in JavaScript. Fixed by returning `undefined` up front when `itemProfileIds` is empty, so an empty/unresolved cart shows every shipping option instead of only Brievenbus.
- **Applying a promo code always showed "That promo code is not valid.", even for a 500 or a missing-cart error** (`app/components/cartSummary.vue`, `onApplyCode`): the component's `catch` block discarded the real server error message. Now shows `error.statusMessage` when present, falling back to the generic message.
- **A remove button was shown on automatic (non-customer-entered) promotions** (`app/components/cartSummary.vue`): now hidden via `v-if="!promotion.is_automatic"`, since removing one there looked like it worked but Medusa just re-applied it on the next cart refresh.
- **Internal SSR-to-SSR fetches never forwarded `Set-Cookie` to the browser** (`app/composables/useCart.ts`, `useCustomer.ts`, and every page that pre-fetches the shared `'cart'`/`'current-customer'` keys): Nuxt/Nitro's internal fetch for a relative URL during SSR runs the target route against its own `H3Event`, so a cookie a route set or deleted (e.g. `checkout/complete.post.ts` clearing the cart cookie, or `cart/index.get.ts`/`account/me.get.ts` clearing a stale one) never reached the page's own response. Fixed with a new `forwardSetCookie` util (`app/utils/forwardSetCookie.ts`, using Nuxt's documented `onResponse` + `appendResponseHeader` pattern), wired into every affected `useFetch` call. Note: `useFetch` dedupes by key, so the fix had to go on whichever call with a given key runs first (a page's own pre-fetch), not just the composable's internal call — the composable's own `onResponse` still matters for standalone usage (e.g. the navbar's cart badge) and for `refresh()` calls.
- **`.devcontainer/devcontainer.json` failing `bun run format:check`** and **home page / showcase-carousel test failures** (`test/nuxt/home-page.test.ts`, `test/nuxt/showcase-carousel.test.ts`) were found to already be resolved by earlier commits on `main` (the devcontainer file is already formatted; the tests already match the current `useSeoMeta` title/description and the carousel's `h-100` class) — the known-issues entries were just never removed after those fixes landed.
